1 Introduction

1.1 Purpose

This document defines the functional design of the EWS Annual Report Extraction Agent — a system that automatically extracts structured financial data from Indian annual report PDFs and populates a predefined Excel template with Balance Sheet, Profit & Loss, and Cash Flow data.

1.2 Design Philosophy

LLM-first, deterministic-validation architecture — the system uses the on-prem LLM (Qwen2.5-7B-Instruct) as the primary method for page identification, statement type detection, and data mapping. Deterministic algorithms (pattern matching, fuzzy string matching, text parsing) serve as validation and fallback, ensuring robustness when LLM is unavailable.

Definition — LLM-first: An architecture where the LLM is the primary processing path for critical decisions (page identification, statement type detection, data mapping). Deterministic methods validate and supplement LLM results, catching errors and expanding coverage. A quick deterministic check skips the LLM call when standard titles find all statements (~70% of cases), optimising cost.
Definition — Deterministic-validation: Deterministic algorithms serve as validation (cross-checking LLM results, expanding continuation pages) and fallback (when LLM is unavailable or returns invalid results). They are NOT the primary method — they ensure the LLM's probabilistic output is grounded in rule-based verification.

4 Step Definitions & Cases

Each step below includes: definition, flowchart with decision branches, and case tables describing what happens in each scenario.

4.1 Step 1 — Find Financial Statement Pages

Definition — Find Pages: The process of scanning every page of a PDF to identify which pages contain the Balance Sheet, Statement of Profit & Loss, and Cash Flow Statement. This is the most critical step — wrong pages lead to wrong data extraction.
Definition — Title Pattern: A regex pattern that matches the title of a financial statement (e.g., balance\s+sheet, statement\s+of\s+profit). Patterns are applied in two tiers: strict (Pass 1) and lenient with context (Pass 2).
Definition — Line-by-line Validation: A filter that ensures a pattern match is a title (not a reference like "see the Balance Sheet on page 47"). A match is a title if it starts within the first 5 chars, the line is ≤ 70 chars, or the match is within the first 40% of the line.

4.1.1 Title Pattern Matching — Cases

CaseConditionBehaviourExample
Case A Strict pattern match in first 10 lines, line-by-line validation passes Pass 1 Hit Page added to statement list "Balance Sheet" on line 2
Case B Strict pattern match but line-by-line validation fails (match too far into line) Pass 1 Miss Rejected as reference, not title "Refer to the Balance Sheet on page 47"
Case C Lenient pattern match with context (e.g., "Standalone" prefix or "As at" suffix) Pass 2 Hit Page added after context verification "Standalone Balance Sheet as at March 31"

A quick deterministic check can skip this step (~70% of cases) when standard Schedule III titles find all 3 statements.

4.2 Step 2 — Detect Financial Year

Definition — Financial Year (FY): Indian financial year runs April 1 to March 31. FY "2017-18" means the year ending March 31, 2018. The system always returns the ending year (2018, not 2017) because that is the year used in column headers like "As at March 31, 2018".
Definition — target_year: The detected ending year passed through the entire mapping pipeline to ensure the correct data column is selected when headers contain multiple years (current year vs. previous year).

4.3 Step 2b — Statement Type Detection & Page Filtering

Indian annual reports that include subsidiaries present two versions of each financial statement — Standalone and Consolidated. The system must (a) detect which type each page belongs to, (b) filter to a single type, and (c) label the result. This is a two-phase process: Phase 1 — Page Filtering (_prefer_standalone()) runs before extraction to select which pages to parse; Phase 2 — Type Detection (_detect_statement_type()) runs after to label the result.

Definition — Standalone: Financial statements representing only the parent company (not including subsidiaries). Required by Schedule III of the Companies Act, 2013. Most Indian companies present standalone statements first, followed by consolidated.
Definition — Consolidated: Financial statements combining the parent company and all its subsidiaries into a single economic entity. Also required by Schedule III when the company has subsidiaries. Consolidated statements aggregate all group entities as if they were a single reporting entity.
Definition — Statement Type Auto-Detection: A two-layer detection process. Primary: The LLM detects statement type as part of the page identification call (find_pages_by_llm() returns statement_type alongside page numbers — no extra LLM cost). Secondary/validation: The deterministic _detect_statement_type() scans each financial statement page's title area (first 10 lines) for "Standalone" or "Consolidated" keywords, counts indicators, and cross-validates the LLM result. When both exist, standalone is preferred. If LLM type is "Not specified", deterministic result is used.
Definition — Title Area: The first 10 lines of text on a PDF page. Indian annual reports typically place the statement type label ("Standalone" or "Consolidated") in the title area, often as a prefix to the statement name — e.g., "Standalone Balance Sheet" or "Consolidated Statement of Profit and Loss".

4.3.1 Phase 1 — Page Filtering (_prefer_standalone)

Runs before table extraction. For each statement type (BS, P&L, CF), if multiple pages were found, this function classifies each page as Standalone or Consolidated and filters to keep only standalone pages. This prevents the system from extracting data from consolidated statements when standalone is available.

CaseConditionBehaviourExample
Case A Only 1 page found for a statement Skip No filtering needed; return page as-is BS found on page 47 only
Case B Multiple pages; some labelled "Standalone", some "Consolidated" Filter Keep standalone pages; discard consolidated BS pages: [47, 48, 49, 50] → standalone: [47, 48] → return [47, 48]
Case C Multiple pages; ALL labelled "Consolidated" Fallback Standalone bucket empty → return all pages Only consolidated BS found → use it
Case D Page has no "Standalone"/"Consolidated" keyword in title area Assume standalone Unlabelled pages go to standalone bucket Page 47 says "Balance Sheet" with no prefix → treated as standalone
Case E PDF read error on a page Graceful Exception caught; return original unfiltered list Corrupt page → no filtering applied

4.3.2 Phase 2 — Type Detection (_detect_statement_type)

Runs after page filtering. Scans the filtered pages to determine and label the statement type. This label is stored in ExtractionResult.statement_type and written to the Meta Data sheet. It is a metadata label only — it does not affect which pages are extracted (that was already decided in Phase 1).

4.3.3 Why Standalone is Preferred

Definition — Standalone Preference: When both standalone and consolidated versions of a financial statement exist, the system extracts from the standalone version by default. This is a design choice, not a limitation — the user can choose to process consolidated statements by modifying the filtering logic.

Reasons for Standalone Preference

#ReasonExplanation
1 Regulatory focus Most Indian financial analysis (RBI, SEBI, MCA filings) requires standalone data. Credit assessments, ratio analysis, and compliance checks typically use standalone figures.
2 Data cleanliness Standalone statements have simpler structures — no inter-company eliminations, no minority interest lines, no associate/JV adjustments. This means fewer mapping ambiguities.
3 Template alignment The Excel template is designed for Schedule III standalone format. Consolidated statements have extra line items (Minority Interest, Share of Associates, etc.) that don't map to the current template.
4 Consistency Companies without subsidiaries only have standalone statements. Preferring standalone ensures consistent output format regardless of whether the company has subsidiaries.
5 Ordering convention Indian annual reports present standalone statements before consolidated. The first match in Step 1 (Find Pages) is typically standalone, so the default page list already leans standalone.
Limitation: If a company has only consolidated statements (rare but possible for holding companies), the system will correctly detect and use consolidated data. However, the template may not have rows for consolidated-specific items like "Non-controlling interest" or "Share of profit of associates". These items will appear in the Raw sheets but not in the mapped output.

4.4 Step 3 — Extract Financial Statement Tables

Definition — Gridless Table: A table in a PDF that has no visible borders or grid lines. Indian annual reports typically use gridless tables where columns are implied by spatial positioning. pdfplumber.extract_tables() returns empty for these, but extract_text() works perfectly.
Definition — Line-by-line Parsing: Each text line is scanned right-to-left for numeric values. Everything before the first numeric value is the label. This handles the common Indian annual report format where labels are left-aligned and values are right-aligned.
CaseConditionBehaviour
Case A Normal line: "Inventories 2 1,234.56 1,100.00" Label = "Inventories 2", note_ref = "2", values = [1234.56, 1100.00]
Case B Negative value: "Finance costs (567.89) (450.00)" Parentheses → negative: values = [-567.89, -450.00]
Case C Section header: "Non-current assets" Marked as is_section_header=True; subsequent rows assigned to this section
Case D Total row: "Total Assets 10,000.00 9,500.00" Marked as is_total=True; excluded from mapping (not a leaf item)
Case E CID-font text: "[CID:12]alance [CID:45]heet" CID placeholders stripped before matching; fuzzy matching handles fragments
Case F Continuation page (no statement title) All lines parsed; section tracking persists from previous page

4.5 Step 4 — Map Extracted Data to Template

Definition — Keyword Alias: An explicit mapping from a PDF row label to a template item, used when fuzzy matching would fail. Example: "right of use assets" → "(iv) Others (to be specified)" in Non-current assets. Aliases handle company-specific terminology.
Definition — Fuzzy Matching (token_sort_ratio): A string similarity algorithm that sorts tokens (words) in both strings before comparing. This handles word reordering — e.g., "Assets Tangible" still matches "Tangible Assets". Score range: 0–100.
Definition — Section-aware Scoring: A bonus/penalty system in fuzzy matching. If the PDF row and template item are in the same section (e.g., both "Non-current assets"), the match score gets +15. If they're in different sections, the score gets −20. This prevents cross-section mismapping.
Definition — Two-pass Optimal Assignment: Pass 1 collects ALL (pdf_row, template_item, score) candidates. Pass 2 assigns optimally by processing in descending score order (greedy), ensuring each PDF row and template item is used at most once.

Definition — Default Zero: A value of 0 automatically assigned to template items that are commonly absent in Indian annual reports (e.g., Goodwill, Biological Assets, Discontinued Operations). These can be overridden by notes extraction via the smart merge mechanism.

10 Indian Financial Reporting Standards

The EWS extraction system is designed specifically for Indian annual reports. Its LLM-first architecture is enhanced because Indian financial reporting is governed by a highly standardised framework — Schedule III of the Companies Act, 2013 and the Indian Accounting Standards (Ind AS). This section explains how these standards underpin every step of the pipeline.

Key Insight: Schedule III and Ind AS provide the standardised vocabulary that makes both LLM and deterministic methods effective. The LLM understands financial terminology because it's trained on standard reports; fuzzy matching and keyword aliases work precisely because the terminology, structure, and ordering of line items are prescribed by law. The standards are the hidden foundation that makes the system reliable — and the LLM-first approach leverages this standardisation for even higher accuracy.

10.1 Schedule III — Companies Act, 2013

Definition — Schedule III: A schedule appended to the Companies Act, 2013 that prescribes the exact format of the Balance Sheet and Statement of Profit & Loss for every company registered in India. It mandates the order of line items, their grouping (Non-current vs Current), and the minimum disclosures required. All Indian companies (except banking, insurance, and Section 8 companies) must follow this format.

10.2 Ind AS — Indian Accounting Standards

Definition — Ind AS: Indian Accounting Standards, converged with IFRS (International Financial Reporting Standards). Mandatory for listed companies and large unlisted companies (net worth ≥ ₹250 crore) since April 2017. Ind AS governs recognition, measurement, and disclosure of financial items — while Schedule III governs presentation format.

10.2.1 Key Ind AS Standards Affecting the System

Ind AS 1 — Presentation of Financial Statements

What it prescribes:

  • Minimum line items on the face of BS and P&L
  • Current/non-current classification
  • Comparative information (previous year)
  • Notes structure and cross-referencing

System impact: The template's minimum line items are derived from Ind AS 1's requirements. The "default zero" items (Goodwill, Biological Assets, etc.) exist because Ind AS 1 requires their disclosure even when zero.

Ind AS 7 — Statement of Cash Flows

What it prescribes:

  • Three-activity classification: Operating, Investing, Financing
  • Net cash from each activity must be shown
  • Reconciliation of cash and cash equivalents

System impact: Cash Flow mapping Phase 0 (structural match) relies on the three "Net Cash" summary rows that Ind AS 7 mandates. The Ops → Inv → Fin ordering is standardised.

Ind AS 16 — Property, Plant and Equipment

What it prescribes:

  • PPE must be classified as a separate NC asset category
  • Disclose: cost, accumulated depreciation, impairment
  • CWIP shown separately under NC assets

System impact: Template item "(a) Property, Plant and Equipment" and "(b) Capital work-in-progress" are always present. Keyword alias "cwip" maps to CWIP because Ind AS 16 mandates this line item.

Ind AS 36 — Impairment of Assets

What it prescribes:

  • Impairment losses must be recognised when carrying amount > recoverable amount
  • Disclosed separately in notes

System impact: "Impairment" is a default_zero item — most companies don't have impairments every year, but Ind AS 36 requires the line item to exist. When present, notes extraction picks it up.

Ind AS 109 — Financial Instruments

What it prescribes:

  • Financial Assets and Financial Liabilities as separate categories
  • Sub-classification: amortised cost, FVOCI, FVTPL
  • Disclose fair value hierarchy in notes

System impact: Template has "Other financial assets" and "Other financial liabilities" as distinct line items under both NC and Current sections. Keyword aliases handle company-specific names like "FVOCI investments" or "Derivatives".

Ind AS 112 — Disclosure of Interests in Other Entities

What it prescribes:

  • Disclose interests in subsidiaries, associates, JVs
  • Related party disclosures (cross-ref Ind AS 24)

System impact: OFI item "Related Party Disclosures" is extracted from Notes. The notes keyword alias "related party" maps to this template item. Ind AS 112/24 mandate this disclosure.

Ind AS 101–103 — First-time Adoption, Changes, Events

What they prescribe:

  • Ind AS 101: First-time adoption transitions
  • Ind AS 102: Share-based payments
  • Ind AS 103: Business combinations

System impact: "Goodwill" (from Ind AS 103 business combinations) is a default_zero item. "Other equity" captures Ind AS 101 transition adjustments. These are rare but standardised.

Ind AS 12 — Income Taxes

What it prescribes:

  • Current tax + deferred tax must be shown separately
  • Deferred tax assets (NC) and deferred tax liabilities (NC)

System impact: Template has "Deferred tax assets (net)" under NC Assets and "Deferred tax" under NC Liabilities. These are always-present items per Ind AS 12.

10.3 Standards → System Alignment Map

Important Limitation: The system is designed for Indian annual reports following Schedule III + Ind AS. It will NOT work correctly for: (1) US 10-K filings (US GAAP), (2) UK annual reports (IFRS without Schedule III structure), (3) Banking/insurance companies (different format per RBI/IRDAI regulations), or (4) Pre-Ind AS reports (pre-2017 format). Supporting these would require a different template and mapping dictionary for each regulatory framework.
