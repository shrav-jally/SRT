The most reliable “SOTA” approach for digitized financial PDFs today is a hybrid, mostly deterministic pipeline: use PDF primitives (PyMuPDF/pdfplumber) as the source of truth for text and geometry, add a strong table/layout detector (DocLayout/MinerU/TableFormer) only for ambiguous layouts, and wrap everything in a constraint‑based reconstruction + financial validation layer before emitting JSON/Excel.[0][1][2][3]

Below I’ll break this into concrete stages and choices, tailored to your use case (100–400‑page annual reports, no OCR, “no‑wrong‑values” requirement).

Problem framing

Your task is document understanding, not RAG: input is a fully digital financial PDF, output is structurally faithful tables (hierarchy, merged cells, headers, subtotals) in JSON/Excel with character‑exact values and auditable behavior.[0]

Existing deep models optimize table metrics like TEDS/F1 on datasets such as PubTabNet, while production financial pipelines must instead optimize “never change a single number”, which favors deterministic extraction and explicit validation over end‑to‑end generative models.[1][0]

Core design principles

PDF primitives first, ML second: the PDF already encodes text, fonts, coordinates, and vector lines; any model that “infers” these will be less reliable than reading them directly.[0]
Separate extraction from reconstruction: getting all tokens correctly is mostly solved; the hard part is assigning them to the right row/column/group and proving that structure is correct.[0]
Use ML/VLM only for ambiguity: instead of “convert this table to JSON”, let deterministic algorithms reconstruct 95–99% and ask a model only to resolve specific structural choices (e.g., which header spans which columns).[1][0]

Phase 1: PDF primitive extraction

For your setting (digitized, financial reports), the first stage should be pure PDF parsing:

Use PyMuPDF or pdfplumber to get text tokens with (x,y) coordinates, bounding boxes, fonts, and vector drawing commands (ruling lines, rectangles).[0]
This gives you deterministic, repeatable access to all characters and layout, and avoids the non‑determinism and speed issues you saw with Docling’s neural models on CPU.[0]

You already have strong evidence that pdfplumber matches printed balance sheets value‑for‑value and is ~100x faster and deterministic compared to Docling on your test set.[0]

Phase 2: Table page and region detection

Next, identify which pages contain tables and where on each page the tables are:

A fast heuristic detector over PDF primitives can flag table pages: dense numeric columns, repeated column alignment, horizontal/vertical ruling lines, regular row spacing, etc., so you only do heavy work on ~20/100–300 pages.[0]
For table regions, you can combine:Rule‑based detection using lines + text clusters.
Optional layout models (MinerU’s layout/table detection, DocLayout‑style models, or TableFormer cell detectors) for side‑by‑side tables and complex multi‑column layouts where geometry alone struggles.[2][3][1]

Tools like MinerU explicitly aim to “extract images, image descriptions, tables, table titles and footnotes” and convert tables to HTML/JSON while handling complex layouts, which makes them good candidates for fallback or cross‑checking.[3][4][2]

Phase 3: Table structure reconstruction

This is the real core of your problem: given a set of characters (tokens) and their coordinates in a table region, reconstruct a table model:

Represent tokens as a character graph: nodes are characters/words; edges capture “same row”, “same column”, “aligned”, “same font group”, etc., based on geometric thresholds.[0]
Use clustering on this graph to infer:Rows (segments of vertically overlapping tokens).
Columns (horizontally aligned groups).
Header hierarchies (rows with different fonts/weights/positions).
Merged cells and spanning headers (continuous ranges of coordinates across row/column indices).

This is conceptually similar to what TableFormer does from images—predicting both structure and cell bounding boxes—but you’re starting from precise PDF geometry instead of noisy OCR, which can be more reliable for programmatic PDFs.[5][1]

The important design choice: treat structure construction as a constraint/graph problem, not a pure ML sequence‑to‑sequence problem, so you can reason about correctness and support auditing.[0]

Phase 4: Financial validation and auditing

Because these are financial statements, you can add a domain‑specific validator:

Check totals and subtotals: verify that “Total Assets” equals “Current Assets + Non‑Current Assets”, that column sums match row subtotals, etc., and flag any mismatch.[0]
Detect inconsistent hierarchies: e.g., headings repeated incorrectly, orphan subtotals, or mis‑grouped segments when comparing similar tables (e.g., standalone vs consolidated).[0]
Track provenance: for every JSON cell, record the originating page, coordinates, and raw PDF token so that you can re‑audit and visually inspect errors.

This validation layer is what pushes you closer to “effective 100% accuracy in production”: errors become detectable and traceable instead of silent, and ambiguous cases can be escalated to manual review or a specialized model.[0]

Role of VLMs and table models

VLMs and table‑structure models are still useful, but in a constrained role:

Use a VLM (e.g., GPT‑4.1V‑class) only when your deterministic reconstruction finds multiple plausible mappings—e.g., a header could span columns 2–3 or 2–4; you ask the model to pick between options, not to redraw the entire table.[0]
Use TableFormer‑style models as a fallback for visually complex layouts (dense, multi‑row headers, side‑by‑side grids) where your geometry‑only approach fails; they can propose cell bounding boxes and structure that you then reconcile with the PDF primitives.[5][1]

Literature on TableFormer shows state‑of‑the‑art tree‑editing‑distance scores on complex tables by combining structure decoding and cell bbox detection, but even there the recommended architecture for programmatic PDFs is to extract cell content from the PDF directly while using the model for structure.[1]

Practical stack recommendation

Given your experiments and constraints, a pragmatic “SOTA‑ish” stack for 2026 looks like:

Primary extractor: PyMuPDF + pdfplumber for PDF primitives and text geometry.[0]
Table/page detection: fast heuristic detector over primitives; optional layout/table models from MinerU/DocLayout for tricky multi‑column pages.[2][3][0]
Structure reconstruction: custom character‑graph + constraint‑based reconstruction engine, inspired by TableFormer’s structure/token separation but built on deterministic PDF coordinates.[1][0]
Validation: financial consistency checks (totals, subtotals, cross‑footing), hierarchy sanity, and confidence scoring per table/page, with provenance metadata.  
Targeted AI: VLM or table‑structure model invoked only on low‑confidence pages to resolve specific structural ambiguities; its outputs are checked against primitives and validators rather than directly trusted.[1][0]

This isn’t “one magical SOTA model”, but it is aligned with how the strongest open‑source systems (MinerU, Docling) and recent table‑structure research are evolving: hybrid, multi‑stage, and deterministic at the core, with ML reserved for ambiguity and complex layouts.[6][3][2][0]

You have exactly the right intuition for a pragmatic, shipping-focused architecture. The idea is: Use cheap heuristics to find the tables, use a VLM to do the heavy lifting of structure/extraction, and use a deterministic check against PDF primitives (pdfplumber/PyMuPDF) to guarantee 100% accuracy.

This entirely bypasses the need to write complex constraint solvers for table reconstruction, while still achieving your "no-wrong-values" requirement.

Here is how you actually build this pipeline:

1. The Fast Heuristic Detector (Page Filtering)

You don't want to send 300 pages to a VLM. You need a fast script that runs in seconds to find the ~20 table pages.

Instead of ML, use PyMuPDF (or a fast rust port like tablers or pdf-inspector) to scan the primitives of each page. A page likely contains a table if it meets 2 or 3 of these conditions:[0][1]

Line density: The page contains a high number of explicit vector drawing lines (e.g., page.get_drawings() in PyMuPDF). Most financial tables have at least horizontal ruling lines.
Numeric density: Extract all text (using a fast text extractor). If >20% of the non-whitespace characters on a page are digits (0-9), it's almost certainly a financial schedule.
Whitespace / Alignment: If you look at the $x$-coordinates of the words, table pages have strong vertical "bands" of text (columns) separated by empty space. 
PyMuPDF/pdfplumber default table finders: Both libraries have built-in find_tables() or extract_tables() methods. While they might fail at reconstructing complex headers perfectly, they are very good at simply detecting the bounding box of a table.[2][3]

Result of Step 1: You narrow down a 300-page PDF to just the 20 bounding boxes (crops) that actually contain tables. 

2. The VLM Extraction

Render those 20 specific bounding boxes as high-res images and pass them to a VLM (like GPT-4o, Claude 3.5 Sonnet, or Gemini 1.5 Pro). 

The Prompt: 
"This is an image of a financial table. Convert it perfectly into a JSON array of objects. Preserve all hierarchical headers by flattening them into the keys (e.g., 'Assets_Current_Cash'). Output ONLY the numbers as they appear, do not do any math. Format output as JSON."

The VLM is excellent at visual structure: it will figure out the merged headers, the indented rows, and the multi-line text wraps that trip up basic scripts. However, VLMs hallucinate numbers (e.g. turning 999.54 into 999.45). This is where your validation layer comes in.[4]

3. The Deterministic Validation Layer (The Guardrail)

This is the magic step that guarantees your 100% accuracy requirement without needing a custom table reconstruction algorithm.

You have two sets of data:

The VLM JSON Output: Perfect structure, but untrusted numbers.
The pdfplumber Output: Perfect text/numbers (extracted from the exact same bounding box), but no structure.

The algorithm to match them:

Extract a raw, unformatted "bag of words/numbers" from the PDF bounding box using pdfplumber.extract_text(). Use a regex to pull out every single numeric token (e.g., ["100.5", "20.0", "150", "(40)"]).
Do the exact same thing to the JSON values output by the VLM.
Compare the two lists sequentially or via subset checking.If the sequence of numbers in the VLM output exactly matches the sequence of numbers in the raw PDF layer, the VLM did not hallucinate. You can confidently save the JSON.
If there is a mismatch (e.g., the VLM dropped a column or transposed a digit), you flag that specific table.

Why this is the best pragmatic approach

This gives you exactly what you asked for:

No training/building complex models: You just write API calls and standard Python regex/matching.
Speed: You only run VLM inference on ~20 regions, not 300 pages.
Safety: The VLM cannot sneak a hallucinated number into your database because it must pass the deterministic pdfplumber check to be accepted.[4]
Graceful degradation: If a table fails the validation check, it simply kicks out an alert for manual review, rather than silently inserting bad data into a financial system.

If borderless tables (like standard balance sheets with no ruling lines) are common, simple primitive-based heuristics might miss them or capture them poorly. The current State of the Art for lightning-fast, 100% table discovery (even for borderless, complex layouts) without slowing down the pipeline is DocLayout-YOLO (or a similar YOLOv8/v10 table detection model).[0][1]

Here is why this completely solves your "what if it's borderless" problem, while fitting perfectly into the VLM + pdfplumber pipeline:

1. Why YOLO for Table Detection?

Instead of manually writing heuristics to look for lines or text density, you convert each PDF page to an image and run it through a tiny object-detection model. 

It detects borderless tables easily: YOLO models trained on datasets like DocLayNet (which contains thousands of financial reports) learn the visual gestalt of a table (alignment, white space, numeric columns) rather than relying on drawn borders.[1][0]
It is incredibly fast: YOLO models run in milliseconds. Even on a CPU, you can scan a 300-page PDF in a few seconds. This satisfies your "lightning fast" requirement.[2][0]
High Recall (100% Discovery): You can set the confidence threshold slightly lower (e.g., 0.25) to guarantee you never miss a table. As you noted, getting a little extra non-table data is fine because the VLM will filter it out, but missing a table is catastrophic.[1]

The Perfected Pipeline

If you implement DocLayout-YOLO for the first step, your pipeline is bulletproof:

Step 1: Lightning Fast Discovery (DocLayout-YOLO)

Convert the 300-page PDF into 300 low-resolution images.
Pass them through DocLayout-YOLO (or keremberke/yolov8m-table-extraction).[2][1]
The model outputs bounding boxes [x1, y1, x2, y2] for every table it finds, whether bordered or borderless.[1]
Time cost: ~10-15 seconds for the entire PDF.

Step 2: VLM Structure Generation

Crop those specific bounding boxes from the high-resolution PDF pages.
Send just those ~20 image crops to your VLM. 
The VLM returns the perfect hierarchical JSON structure. If the YOLO box accidentally included a paragraph of text above the table, the VLM will naturally ignore it because you prompted it to extract only the table.[3]

Step 3: The pdfplumber Guardrail

Pass those exact same [x1, y1, x2, y2] bounding box coordinates to pdfplumber (page.crop((x1, y1, x2, y2)).extract_text()).[4][1]
Extract the raw, 100% accurate text layer numbers.
Compare the raw numbers to the VLM JSON numbers.
If they match perfectly: Save to database.
If they don't match: Flag for manual review.

Does this actually work for borderless tables?

Yes. YOLOv8 variants specifically trained on document intelligence (like the keremberke/yolov8m-table-extraction model on HuggingFace or OpenDataLab's DocLayout-YOLO) are trained explicitly on bordered and borderless tables. They look at the spatial arrangement of text blocks, not just lines.[0][1]

By using YOLO just to find the table, the VLM to structure the table, and pdfplumber to verify the numbers, you are using each tool for exactly what it is best at, avoiding complex manual rule creation entirely.

Product 1 ingestion pipeline (SOTA stack)
High-level stages
PDF loading & primitives extraction
Use PyMuPDF or pdfplumber to:
Extract pages, text runs, character boxes, fonts, and simple rectangular bounding boxes.[linguistics.rub]
Capture PDF metadata and object references.
Build the token registry per page and coarse reading order (sort by y, then x, with heuristics for multi-column layouts).
Page rendering & layout detection
Render each page to an image (e.g., 300 DPI PNG).
Run a layout detection model (DocLayout-YOLO, PP-DocLayout, etc.) to detect:
Tables (with border vs borderless).
Headings (different levels).
Figures, captions.
Lists, footnotes.
Each detection is mapped back to PDF coordinates and associated with primitive tokens inside its bounding box.
Table page detection & region cropping
From layout detections:
Mark pages with table regions (including borderless schedules common in IFRS illustrations).[assets.kpmg]
Define table candidates as regions containing:
Dense numeric tokens aligned in columns.
Repeated row labels on the left.
Crop the region and gather all included tokens as primitive candidates for that table.
Table structure reconstruction
Combine three sources of evidence:
Geometry-based grid inference
Cluster tokens into columns using x-coordinates and alignment (e.g., Gaussian mixture on x centers).
Cluster tokens into rows using y-coordinates and baseline alignment.
Use heuristics to identify merged cells (large bounding boxes spanning multiple column bands).
TableFormer-like model
Feed the cropped image + associated tokens into a transformer-based model that predicts:
Cell boundaries (grid graph).
Row/column header roles.
Relationships between header cells and data cells.
VLM assistance (for ambiguity only)
In cases where geometry and TableFormer disagree (e.g., ambiguous header spanning two columns, or complex multi-level headers), crop the header region and ask a VLM:
“For this table header, map visual headers to underlying columns. Return column-role assignments.”
VLM output is only structure (roles, spans), never numbers; numeric tokens remain untouched.
The final table structure is a merged, validated grid:
Start with geometry-based grid.
Overlay TableFormer predictions.
Apply VLM-based corrections only where needed.
Construct rows, columns, and cells with explicit rowspan and colspan.
Section hierarchy building
Heading detection
Merge layout model detections with font analysis (size, weight, all caps, extra spacing) to classify headings and infer levels (H1–H4).
Semantic tagging
Use rule-based and LLM-assisted normalization:
“Statement of Profit and Loss and Other Comprehensive Income” → financial_statements_pl.[ifrs]
“Notes to the Financial Statements” → notes_to_accounts.
“Corporate Governance Report” → governance.
Section tree construction
Sort headings by page and position.
Build a tree using heading levels (outline-style).
Assign blocks and tables to the nearest enclosing section based on spatial overlap and reading order.
Metadata extraction
Use a constrained NLP/LLM pipeline over canonical tokens for:
Company name, FY end date, reporting framework, currency, auditor opinion type.[pwc]
All metadata extraction paths include token references and confidence scores; extracted values are stored in document_metadata.
“No-wrong-values” numeric validation Core principle: all numbers in tables must be traceable back to primitive numeric tokens without alteration. Strategy:
For each table region:
Collect primitive numeric tokens (regex-based numeric recognition, including parentheses, negative signs, comma separators).
For each cell:
Record numeric_tokens (token IDs) and a text field (joined raw text).
Parse parsed_numeric via deterministic rules:
Remove separators, interpret parentheses as negative, respect plus/minus.
Do not apply unit scaling at this stage (Crore/Lakh/Million is a tag, not a transform).
Validation process:
Re-encode parsed_numeric back to a string using the same formatting rules and compare with raw cell text (modulo whitespace).
Confirm that the set of structured numeric values equals the set of primitive numeric tokens in value and multiplicity (i.e., no extra or missing numbers).
If any mismatch:
Mark validation.status = "FAILED".
Log mismatches in validation.mismatches.
Option: flag the table as unsafe for downstream extractors, or require manual QA.
This ensures domain extractors see either validated tables or clearly flagged exceptions, avoiding silent numeric corruption.

EWS Financial Data Extraction (VLM)

This project provides an automated, end-to-end pipeline for extracting complex financial tables (Balance Sheet, Profit & Loss, Cash Flow) from Indian Annual Report PDFs. It uses a Vision Language Model (VLM) powered by Deloitte's On-Premise Qwen3-VL to robustly process scanned, noisy, or natively digital PDFs.

?? Architecture & Workflow

The pipeline is designed to handle extremely long and noisy PDFs gracefully:

Upload & Ingestion (FastAPI):

Users upload an Annual Report PDF via a sleek, modern web UI.
The file is ingested and routed to the extraction pipeline.


Heuristic Discovery & Parsing (PyMuPDF):

The document's text layer is parsed to find the Table of Contents (TOC).
Pages are scanned for keywords indicating financial statements.


VLM Classification Fallback:

For heavily scanned or "corrupted" PDFs where the text layer is missing or garbled, the pipeline routes the page images to a specialized VLM classifier.
The classifier identifies which pages contain the Standalone or Consolidated Balance Sheet, P&L, and Cash Flow.


VLM Tabular Extraction (LangChain):

Identified pages are converted to base64 images and sent to the core Vision Language Model (Qwen3-VL).
The model follows strict prompt instructions to extract the tabular data into structured, hierarchical JSON (sections, line items, note numbers, current/previous periods).
Resilience: The extraction layer features a highly robust retry mechanism that validates the LLM's output. If the model hallucinates or outputs malformed JSON, the pipeline automatically catches the error and retries the prompt.


Excel Reconstruction (OpenPyXL):

The structured JSON is passed to the Excel Builder, which dynamically reconstructs the financial tables into a professional, multi-sheet Excel workbook.
Both the JSON and the Excel workbook are dynamically bundled into a single ZIP file and streamed back to the user.


🚀 Recent Enhancements (Phases 2-4 & Sprint 3)

During our most recent pair-programming sessions, we fundamentally upgraded the extraction architecture to an enterprise-grade "Master Data" model, and hardened the extraction logic:

Section Registry (Phase 2): Replaced raw taxonomy mappings with a Master Sections layer that dynamically aggregates contiguous pages of the same category into structural blocks.
Table Inventory (Phase 3): Formalized table detection to log all potential tables (and whether they require VLM processing) into a centralized table_inventory.
Generic VLM Router (Phase 4): The extraction pipeline now seamlessly routes all complex non-financial tables (e.g., Shareholding Pattern, Segment Info, SOCE) to a dynamic, generic VLM extraction engine, while preserving the highly-optimized legacy VLM engine exclusively for the core 3 financial statements.
Universal Excel Generator: Completely overhauled excel_builder.py to ensure the generated Excel workbook is an exact 1:1 reflection of the Master Data JSON. The exporter dynamically creates a dedicated Excel sheet for every Category, and prints out beautiful, cleanly wrapped text blocks and formatted table grids for every Subcategory.
Schema Bleeding & Flattening Fixes (Sprint 3): Hardened extraction routing (content_extractor.py) to use strict explicit target mapping, completely solving the "Schema Bleeding" issue where overlapping text heuristics caused data extraction to overwrite adjacent targets. Additionally, overhauled workbook_population.py to index the hierarchical JSON using exact lookups, fixing the "Flattening Collisions".
Pydantic Resilience (Sprint 3): Re-wrote canonical schemas to use Optional types, preventing catastrophic validation failures when the LLM returns null for missing parameters.
RAG & Semantic Chunking (Sprint 3): Eliminated naive token truncation (which caused massive data loss in the MD&A section). Yes — this is the right pivot for the demo. A strong canonical JSON plus a custom field extraction layer is much more general, easier to sell, and easier to demo than locking yourself into MSME right now. A schema-driven extractor is also exactly how universal IE systems are usually framed: a fixed document representation plus a task/schema prompt that tells the system what entities/attributes/relations to extract.[0][1]

Your sample spec is straightforward if you model it as a field registry over the canonical document, not as hardcoded Python for every category. The winning design is: Product 1 emits a lossless canonical document with tables, tokens, sections, and provenance; Product 2 accepts a user-defined extraction schema like “Category / Subcategory / Entity Name / Entity Type / Description / Extraction Mode” and returns structured results with status and provenance for each requested field.[2][3]

What to build now

Build a Custom Extraction Spec Engine on top of the canonical JSON, not a separate MSME-only extractor. The spec should define fields such as Financial Data -> Balance Sheet -> X -> Direct Mapping or Demographics -> Employee Count -> Y -> Inference Based, and the engine should resolve each field against the canonical document using either deterministic matching or constrained LLM inference.[1][3]

For tomorrow’s demo, the output should be one JSON array of requested fields, where every field includes: request metadata, extracted value, status, confidence, explanation, and provenance down to section/table/cell/token where available.[4][2]

Recommended field schema

Use a registry row model like this for every custom field request:

Field Purpose
field_id Stable machine identifier for the requested output.
category Top-level grouping like Financial Data or Demographics.
subcategory Narrow grouping like Balance Sheet or Employee Count.
entity_name The exact business label requested by the user.
entity_type For example metric, text_fact, count, date, table, list.
description Human description of what the field means.
extraction_mode DIRECT_MAPPING, INFERENCE_BASED, or DERIVED.
synonyms Candidate phrases to match in canonical sections/tables.
expected_section_types Likely places to search first.
expected_value_type string, number, currency_amount, integer, list, etc.
required Whether absence is important.
output_cardinality single, multi, table, list.

This gives you a proper machine-readable extraction contract, and it matches the idea of schema-controlled extraction in universal IE rather than task-specific code paths.[0][1]

Extraction modes

Use three modes only:

DIRECT_MAPPING: exact or synonym-based retrieval from canonical sections/tables, best for Balance Sheet items, named sections, auditor name, employee count if explicitly printed.
INFERENCE_BASED: use the company VLM/LLM over a small canonical snippet, never the raw PDF, when the answer is implied but not printed as a neat label.
DERIVED: computed from already extracted canonical values, with formulas and dependencies recorded.

This separation matters because it lets you say in the demo: “The system supports exact lookup, contextual inference, and calculated outputs, all from the same canonical JSON.” That is much stronger than “we built a bunch of fixed extractors.”[3][1]
